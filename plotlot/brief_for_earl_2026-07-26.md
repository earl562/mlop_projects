# PlotLot agentic harness — verification and production database reconciliation

Last updated: 2026-07-27T04:51:01Z  
Working branch: `Phat` (synced with `origin/Phat`)

## Objective

Prove the PlotLot agentic harness is correctly built and operational, and make it durable. Every
tool call — from REST, MCP, or CLI — must pass a single governed path that authorizes by risk
class, enforces a spend budget, requires human approval for external writes, emits lifecycle
events, and persists an audit record with its evidence. Any divergence between the ORM models and
the live database must surface immediately rather than silently disabling that path.

## Accomplished

- Harness verified across all three transports against live production: REST, MCP, and CLI each
  route through the same `HarnessRuntime` and return identical governed results.
- Harness and storage test suite passes 77 checks, including new coverage for schema-drift
  detection.
- Root-caused a production failure that had silently disabled the harness's entire persistence
  layer: `POST /api/v1/tools/call` returned 500 with `column workspaces.owner_user_id does not
  exist`. No tool call was being audited, no evidence persisted, and no approval request could be
  created, so external-write approvals could block an action but never complete one.
- Identified two stacked causes. Alembic was installed and scaffolded, but two feature branches
  had both reused revision IDs `007` and `008`, making the revision graph unresolvable and
  migrations unrunnable. The app therefore fell back to `Base.metadata.create_all`, which only
  creates absent tables and never alters an existing one, so models that gained columns left the
  live tables behind. Divergence had reached 39 missing columns across 8 tables.
- Repaired the migration graph: unique revision IDs, rewired chain, a merge revision producing a
  single head, and a new revision covering two model tables that had never appeared in any
  migration. Verified single head, zero duplicate IDs, zero dangling references, full base→head
  chain rendering valid SQL, and 26/26 model tables covered.
- Reconciled the production database under staged controls: read-only reconnaissance first;
  confirmed the 16 affected harness tables were empty and foreign-key isolated so a rebuild could
  not cascade into real data; backup branch taken; exact DDL reviewed before execution; executed
  as a single transaction; `ordinance_chunks` (41,141 rows, the only table holding real data)
  deliberately excluded from scope and verified intact afterward.
- Post-reconciliation verification against production: zero schema drift on all 16 harness tables;
  REST and MCP each list 25 tools and execute governed calls successfully; external writes on both
  transports correctly return `pending_approval` with a persisted `ApprovalRequest`; an expensive
  read with zero budget is correctly gated; `ToolRun` rows persist with full input and output.
- Added startup schema-drift detection. The application now compares live schema against the ORM
  models on boot and logs an explicit error naming any missing table or column, converting a
  silent multi-week failure into an immediate signal. It is non-fatal by design so a degraded API
  still boots.

## Not yet accomplished

- `ordinance_chunks.updated_at` remains absent by deliberate scope exclusion. The drift guard
  reports it on every boot; a permanent warning erodes the value of the alarm, so this needs a
  go/no-go decision. Adding a nullable timestamp column is metadata-only in PostgreSQL and does
  not rewrite the table.
- Six `ToolRun` and two `ApprovalRequest` verification rows remain in the production audit table
  and can be cleared on request.
- Which branch Render actually deploys is still unconfirmed, so none of this is proven to reach
  production users.
- Two harness slices remain unbuilt: mapping `HarnessEvent` to the chat SSE stream so the frontend
  receives one event schema across transports, and unifying chat's in-memory `SessionStore` with
  the harness `ContextBroker`.
- The deal-watcher agent remains scoped but unbuilt, and depends on the persistence layer
  repaired today.

## Blockers

1. Neon is shared with MLflow (~40 tracking tables) and other tables absent from our ORM models.
   `alembic revision --autogenerate` against this database emits migrations that would drop all of
   MLflow's tables and data, because Alembic treats anything missing from the models as a
   deletion. No autogenerated migration may be applied to this database without line-by-line
   review. Today's fix was hand-written for this reason.
2. The Render deploy branch is unknown, so release impact cannot be asserted.
3. Neon storage is at 83.2% of the monthly allowance for this project.

## Path to fix

1. Decide on `ordinance_chunks.updated_at`; add it so the drift guard returns to silent, or record
   an explicit exception so the warning is understood rather than ignored.
2. Confirm the Render service branch, then reconcile `Phat` with whatever branch deploys; `main`
   is 81 commits behind and is not a safe assumption.
3. Establish an explicit release step running `alembic upgrade head` so migrations, not
   `create_all`, own schema on real databases.
4. Complete the remaining harness slices: `HarnessEvent` → SSE mapping, then `SessionStore` →
   `ContextBroker` unification behind tests, as the latter touches grounding logic with a history
   of regressions.
5. Treat the drift guard's output as a release gate; any reported drift means a migration is owed
   before deploy.
